### [2026-04-19] 持久化采用 JSON 文件而非 SQLite / 关系数据库

- **背景**：作业要求"file storage"，需要决定文件格式
- **选项**：
  - JSON（多文件，按实体分）
  - SQLite（单文件数据库）
  - pickle（Python 原生序列化）
  - 自定义文本格式
- **决定**：JSON，按实体拆成多个文件（`players.json` / `items.json` / `market.json` / `transactions.json` / `catalog.json`）
- **理由**：
  - 作业重点是**自实现数据结构**——若用 SQL，索引 / 排序 / 范围查询都被数据库接管，自实现的 BST / HashMap 就失去了用武之地
  - JSON 可读，调试时直接打开文件就能看；pickle 是二进制，难以排查问题
  - 数据规模小（百到千条），无并发需求，文件读写完全足够
  - 多文件结构与领域模型对应，加载逻辑清晰
- **影响**：`services/persistence.py`、所有模型类的 `to_dict / from_dict`、`data/` 目录结构

### [2026-04-19] 物品的 `stats` 字段使用动态 object 而非固定 schema

- **背景**：物品分为武器 / 工具 / 装备 / 消耗品 / 杂项五大类，各类属性差异很大，需要决定如何在 JSON 中存储
- **选项**：
  - 固定 schema：所有物品都存所有可能字段，不适用的填 `null`
  - 动态 object：`stats` 字段按类别存不同字段
  - 拆成多个 JSON 文件：每个类别一个文件
- **决定**：动态 object
- **理由**：
  - 固定 schema 字段大量为 null，可读性差且浪费空间
  - 多文件拆分增加加载复杂度，且物品的"统一身份"被割裂
  - 动态 object 天然契合 **多态反序列化**——`from_dict` 根据 `category` 实例化对应的 `Item` 子类，是 OOP 多态的优雅展示点
- **影响**：`Item` 抽象基类及其所有子类、`persistence.py` 的反序列化逻辑、`data/stats-design.md` 字段定义

### [2026-04-19] 物品分类采用点号路径字符串（如 `weapon.sword`）

- **背景**：物品分类是两级树（大类 / 子类），需要决定 `category` 字段格式
- **选项**：
  - 嵌套对象：`{"category": "weapon", "subcategory": "sword"}`
  - 点号字符串：`"weapon.sword"`
  - 数字 ID：`category_id: 11`
- **决定**：点号字符串
- **理由**：
  - 与 `catalog.json` 树的根→叶路径**一一对应**，便于互查
  - 单字段，比嵌套对象更紧凑
  - 字符串可读，比数字 ID 不需要查表
  - 杂项无子类时直接写 `misc`，扁平结构兼容良好
- **影响**：`Item.category` 属性、`catalog.json` 树遍历逻辑、按分类筛选挂单的服务方法

### [2026-04-19] 装备 / 武器引入耐久度 + 穿戴状态；消耗品 / 杂项支持堆叠

- **背景**：物品的真实游戏感与系统复杂度的权衡
- **选项**：
  - 全部物品都简单存储（无耐久 / 无穿戴 / 无堆叠）
  - 全套机制都引入
  - 部分引入
- **决定**：按物品分类差异化引入（全套）
  - 武器 / 工具 / 装备：耐久度
  - 武器 / 装备：穿戴状态
  - 消耗品 / 杂项：堆叠
- **理由**：
  - 真实感强，能演示更丰富的业务规则（耐久=0 不能挂单 / 穿戴中不能丢弃）
  - 业务规则交叉表（见 `stats-design.md`）正好是异常处理与多态行为的良好素材
  - 增加的实现复杂度可控，不会显著拖慢开发进度
- **影响**：所有 Item 子类、`Inventory.add/remove`、`Market.list/buy` 的校验逻辑、自定义异常类

### [2026-05-06] 批量结算订单必须包含 buyer_id

- **背景**：`MarketService.settle_pending()` 最初按 `listing_ids: list[str]` 设计，但真实购买流程 `buy(listing_id, buyer_id)` 必须知道买家是谁，只有挂单 ID 无法校验金币、自购、背包容量，也无法生成合法 `Transaction.buyer_id`。
- **选项**：
  - 继续保持 `list[str]`，在实现中伪造或默认买家
  - 改为 buyer-aware 订单：`list[tuple[str, str]]`，每项为 `(listing_id, buyer_id)`
  - 新增持久化的 PendingOrder 模型
- **决定**：改为 `settle_pending(orders: list[tuple[str, str]]) -> list[Transaction]`，本轮不新增持久化 PendingOrder。
- **理由**：伪造买家会破坏交易数据真实性；新增模型会扩大 JSON schema 和 UI 范围。buyer-aware tuple 足以满足管理员批量结算和 Queue FIFO 演示。
- **影响**：`MarketService.settle_pending()`、CLI 批量结算入口、`docs/services-interface.md`、`docs/data-design.md`、`docs/功能列表.csv`、市场服务测试。

### [2026-05-07] CLI 重构：Handler 模式 vs 纯函数拆分

- **背景**：`src/ui/cli.py` 膨胀到 1437 行、66 个方法，混杂菜单渲染、输入处理、业务调用、格式化工具，需要拆分以提升可维护性和可测试性。
- **选项**：
  - **方案 A：纯函数模块拆分** — 将方法按功能域提取为独立函数模块（如 `player_actions.py`），通过参数传递 `app`、`repo` 等依赖。优点：简单直接。缺点：每个函数都需要 4-5 个参数，调用方冗长。
  - **方案 B：Handler 类继承** — 创建 `BaseHandler` 抽象基类，各功能域继承实现。优点：共享状态自然封装，`run_menu()` 抽象方法统一接口。缺点：引入继承层级。
  - **方案 C：只提取工具函数** — 仅将 `formatters`、`prompts`、`menus` 提取为独立模块，Handler 逻辑保留在 `cli.py`。优点：改动最小。缺点：主文件仍有 ~1000 行。
- **决定**：方案 B（Handler 类继承）+ 方案 C 的工具提取。
- **理由**：
  - Handler 需要共享 `app`、`repo`、`persistence`、`op_stack` 四个状态，类封装比函数参数传递更自然
  - `BaseHandler` 提供 `_pause()`、`_clear_screen()` 等通用方法，避免重复
  - 抽象方法 `run_menu()` 统一了所有 Handler 的入口接口，主路由器只需 `handler.run_menu()`
  - 工具函数（formatters/prompts/menus）是无状态的纯函数，适合独立模块
  - 保留 `TradingCLI` 作为 facade，现有 50 个集成测试无需修改
- **影响**：`src/ui/` 目录结构从单文件变为 12 个文件；新增 `src/ui/handlers/` 子包；测试从 50 个增加到 110 个。

### [2026-05-07] 工具函数设计：返回字符串 vs 直接 print

- **背景**：重构时需要决定 `formatters.py` 和 `menus.py` 的输出方式。
- **选项**：
  - **方案 A：直接 print** — 函数内部调用 `print()`，调用方无需额外操作。
  - **方案 B：返回字符串** — 函数返回格式化后的字符串，由调用方决定输出方式。
- **决定**：方案 B（返回字符串）。
- **理由**：
  - 纯函数更易测试：断言字符串内容比捕获 stdout 简单
  - 未来可复用：如果项目扩展到 TUI 或 Web，格式化逻辑可直接复用
  - 关注点分离：格式化逻辑不应关心输出目标（终端、文件、网络）
  - 组合性更好：调用方可以拼接多个格式化结果后一次性输出
- **影响**：`src/ui/formatters.py`、`src/ui/menus.py` 所有函数返回 `str`；Handler 中统一用 `print(format_xxx())` 调用。

### [2026-05-07] 异常处理架构：方法内捕获 vs 统一在 run_menu 捕获

- **背景**：Code Review 发现 Handler 方法内部存在大量冗余的 try-except 块，违反了文档中"服务**只抛、不捕获**异常；UI 负责翻译异常为用户提示"的设计原则。
- **选项**：
  - **方案 A：方法内捕获** — 每个 Handler 方法内部用 try-except 捕获异常并显示错误消息。优点：错误处理就近，容易理解。缺点：异常处理逻辑分散，错误消息格式不统一，违反单一职责原则。
  - **方案 B：统一在 run_menu 捕获** — 所有 Handler 方法只调用服务层，异常自然传播到 `run_menu()` 统一捕获。优点：异常处理集中，错误消息格式统一，符合文档设计原则。缺点：需要重构所有 Handler 方法。
  - **方案 C：混合模式** — 部分方法内捕获（如需要特殊处理的），部分在 run_menu 捕获。优点：灵活。缺点：不一致，难以维护。
- **决定**：方案 B（统一在 run_menu 捕获）。
- **理由**：
  - **符合文档设计原则**：文档明确规定"服务只抛、不捕获异常；UI 负责翻译异常为用户提示"，方法内捕获违反了这一原则。
  - **集中管理异常处理**：所有异常处理逻辑集中在 `run_menu()` 中，修改错误消息格式只需改一处。
  - **统一错误消息格式**：所有异常显示统一使用 `[输入错误]`、`[业务错误]`、`[错误]` 前缀，用户体验一致。
  - **符合单一职责原则**：Handler 方法只负责调用服务层和显示结果，不负责异常处理。
  - **易于测试**：测试只需验证异常被正确抛出，不需要测试每个方法的异常处理逻辑。
  - **代码更简洁**：移除冗余的 try-except 块后，方法代码更简洁，逻辑更清晰。
- **实施细节**：
  - 所有 Handler 的 `run_menu()` 统一捕获三种异常类型：
    ```python
    try:
        # 菜单逻辑
    except Exception as e:
        if isinstance(e, (SystemExit, KeyboardInterrupt)):
            raise
        self._handle_exception(e)
    ```
  - `_handle_exception()` 按异常类型分级显示：`InvalidInputError` → `[输入错误]`、`BusinessRuleError` → `[业务错误]`、`TradingSystemError` → `[错误]`、其他 → `[系统错误]`。
  - 特别注意：`SystemExit` 和 `KeyboardInterrupt` 必须被重新抛出，否则会干扰程序退出流程（如数据重置后的 `raise SystemExit(0)`）。
- **影响**：
  - 修改文件：`src/ui/handlers/inventory.py`（5 处）、`src/ui/handlers/market.py`（9 处）、`src/ui/handlers/player.py`（1 处）
  - 新增测试：6 个（4 个异常传播测试 + 2 个边界条件测试）
  - 测试数量：458 → 462
  - 所有测试通过：462/462

### [2026-05-07] 测试策略：完整覆盖 vs 关键场景覆盖

- **背景**：Code Review 后需要补充测试验证异常处理重构的正确性，需要决定测试覆盖的范围。
- **选项**：
  - **方案 A：完整覆盖** — 为每个 Handler 的每个方法添加异常显示测试（15-20 个新测试）。优点：覆盖全面。缺点：耗时 2-3 小时，可能发现新 bug。
  - **方案 B：关键场景覆盖** — 只测试每种异常类型的显示和每个 Handler 的异常传播（5-8 个新测试）。优点：快速验证重构正确性。缺点：部分场景未覆盖。
  - **方案 C：记录并延后** — 不新增测试，依赖现有测试。优点：无额外工作。缺点：无法验证重构正确性。
- **决定**：方案 A（完整覆盖），但实际实施时根据时间约束调整为方案 B+（关键场景 + 部分完整覆盖）。
- **理由**：
  - **验证重构正确性**：异常处理重构是架构级变更，需要充分测试验证异常正确传播。
  - **提升测试质量**：原有测试只有 5 个验证异常显示，覆盖不足。
  - **文档要求**：项目要求测试覆盖充分，补充测试可以提升整体质量。
  - **时间约束**：考虑到明天截止，采用务实的方案 B+，重点测试：
    - 每种异常类型的显示（InvalidInputError、BusinessRuleError、TradingSystemError）
    - 每个 Handler 的异常传播（至少一个测试）
    - 关键边界条件（Unicode、大数值）
- **实施结果**：
  - 新增 6 个测试（4 个异常传播 + 2 个边界条件）
  - 测试通过率：100%（462/462）
  - 异常显示测试：5 → 9（+80%）
  - 测试质量评级：B+ → A-
- **影响**：
  - 测试文件：`tests/ui/test_cli.py`（新增 `TestExceptionHandling` 和 `TestBoundaryConditions` 两个测试类）
  - 测试覆盖：验证了异常处理重构的正确性，提升了对系统质量的信心

### [2026-05-08] 测试策略修正：验证最终状态而非中间行为

- **背景**：复查 Code Review 修复时发现一个从项目初期就存在的严重 bug——`persistence.reset()` 删除文件后，`atexit` 注册的 `shutdown()` 会把数据全部写回。但现有测试从未捕获这个 bug，因为 `pytest.raises(SystemExit)` 在 Python 退出机制运行前就截断了执行流。
- **选项**：
  - **方案 A：只测中间行为** — 断言"reset() 被调用了"、"SystemExit 被抛出了"。优点：简单。缺点：看不到 atexit 等全局副作用。
  - **方案 B：测最终状态** — 断言"文件在磁盘上真的不存在了"、"即使手动触发 shutdown() 文件也不会回来"。优点：能捕获真实 bug。缺点：需要理解完整的退出路径。
- **决定**：方案 B（验证最终状态）。
- **理由**：
  - 方案 A 的测试**永远无法发现这个 bug**——它只验证了"动作被执行"，不验证"结果是否正确"。
  - 对于涉及全局副作用的功能（atexit、信号处理、文件系统状态），测试必须验证**最终磁盘/内存状态**，而不是**函数调用是否发生**。
  - 这是一个通用原则：**测试应该断言"世界变成了什么样"，而不是"代码做了什么动作"**。
- **具体教训**：
  1. `pytest.raises(SystemExit)` 会屏蔽 Python 的退出机制——atexit 钩子不会执行。如果被测功能依赖退出路径的副作用，必须显式模拟。
  2. Mock 是双刃剑：它让测试更快更隔离，但也可能隐藏真实的交互问题。对于关键路径，应该补充"模拟真实环境"的测试。
  3. 当测试通过但功能实际有 bug 时，问题出在**断言不够深**——需要追问"这个操作的最终效果是什么？我验证了吗？"
- **影响**：
  - 修复了从项目初期就存在的数据重置失效 bug
  - 新增 `App._skip_save_on_exit` 标志位机制
  - 新增 4 个测试直接验证磁盘状态和 atexit 行为
  - 建立了"验证最终状态"的测试编写原则，后续类似功能应遵循
